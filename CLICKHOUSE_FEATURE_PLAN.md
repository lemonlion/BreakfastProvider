# ClickHouse feature plan — "Kitchen Analytics"

**Status:** implemented (2026-09-03). Kept as the design record: Appendix A holds the wire captures every
emulator decision rests on. The emulator's own summary of those facts is
[tests/InMemoryEmulator.ClickHouse/README.md](tests/InMemoryEmulator.ClickHouse/README.md).
**Goal:** add a ClickHouse-backed feature to BreakfastProvider that is the same shape and size as the
BigQuery feature, tracked in Kronikol diagrams via `Kronikol.Extensions.ClickHouse`, runnable in
every lane (InMemory / Docker / External SUT) from **all six** component-test suites (xUnit, NUnit,
TUnit, BDDfy, LightBDD, ReqNRoll), with an in-process DuckDB-backed ClickHouse emulator for the
InMemory lane and real ClickHouse in Docker for the other two.

This document is self-contained: §0 orients a reader who has never opened the repo, Appendix A holds
the raw wire captures every emulator decision rests on, and Appendix B is the reproducible spike that
produced them. It supersedes Phases 0–6 of [CLICKHOUSE_INMEMORY_PLAN.md](CLICKHOUSE_INMEMORY_PLAN.md);
that older file remains useful only for the deferred Octonica / native-TCP front-end (its Part 3), and
§10 lists where it is now wrong.

## 0. Orientation for a cold start

**What this repo is.** A reference .NET 10 API (`src/BreakfastProvider.Api`) whose point is its
component-testing approach: the same scenarios run in three lanes (all dependencies in-process,
dependencies in Docker, everything in Docker) from six test frameworks, and every run emits a Kronikol
report with sequence diagrams of the SUT's calls to its dependencies. There is no `CLAUDE.md`; the
conventions live in `.claude/skills/component-tests/` (start with `SKILL.md`, then
`test-infrastructure.md`) and `.github/copilot-instructions.md`.

**How tests run.** `global.json` selects Microsoft.Testing.Platform, so it is
`dotnet test tests/BreakfastProvider.Tests.Component.xUnit/BreakfastProvider.Tests.Component.xUnit.csproj`
(same for the other five). The Kronikol report lands at
`tests/<suite>/bin/Debug/net10.0/Reports/TestRunReport.html`. The lane is chosen by the
`RunWithAnInMemory*` flags in each suite's `appsettings.componenttests.json`; the xUnit and LightBDD
projects have `Configure/switch-to-{inmemory,docker,docker-external-sut,manual-docker-external-sut}.{sh,bat}`
scripts that flip every flag with `sed`; the other four suites are edited by hand (or copy the scripts).
CI (`.github/workflows/ci-main.yml`) runs each suite × {memory, docker, external-sut} as separate jobs
through `_tests.yml` (`_tests-tunit.yml` for TUnit); `.github/scripts/set-inmemory-flags.sh` sets the
flags as environment variables for the Docker jobs.

**Conventions that matter here.** Tests randomise their own keys (`$"Flour-{Guid.NewGuid():N}"`) and
assert only on their own rows, because every backend — emulator or container — is shared by parallel
tests. Health checks are replaced with `NoOpHealthCheck` in the InMemory lane. Event-driven flows are
tested by publishing straight into an in-memory store (`ConsumedKafkaMessageStore`) that an
`IHostedService` in the Shared project subscribes to; the real Kafka consumer is always removed from
DI, in every lane. Routine changes go on `main` (not the `java-twin` branch). Commit messages carry no
attribution lines.

## 1. What "the same size as BigQuery" means

The BigQuery feature is three sub-features on one backend, so the ClickHouse feature is three
sub-features on one backend:

| BigQuery today | Shape | ClickHouse twin |
|---|---|---|
| `IngredientUsage` (`/ingredient-usage`) | POST record · GET summary (GROUP BY) · GET list-by-key | **Order Timings** (`/order-timings`) |
| `IngredientWaste` (`/ingredient-waste`) | POST record · GET list-by-key · DELETE by id | **Equipment Readings** (`/equipment-readings`) |
| `RecipeCosts` (Kafka → BigQuery → gRPC → Kitchen HTTP) | Event-driven, no controller | **Service Times** (Kafka → ClickHouse → gRPC → Kitchen HTTP) |
| `BigQueryConfig`, `AddBigQuery`, `BigQueryHealthCheck`, `ServiceNames.BigQuery` | Wiring | `ClickHouseConfig`, `AddClickHouse`, `ClickHouseHealthCheck`, `ServiceNames.ClickHouse` |
| `InMemoryEmulator.BigQuery` (NuGet) | InMemory lane | **`InMemoryEmulator.ClickHouse`** (new in-repo project, DuckDB-backed) |
| `bigquery-emulator` + `bigquery-init` containers | Docker lane | `clickhouse` container seeded via `docker-entrypoint-initdb.d` |
| 3 scenario files × 6 suites, 6 shared step classes, 5 test models | Tests | Same counts |

The original BigQuery commit (`ba83899`) touched ~15 `src` files and ~45 test files. This feature is
the same **plus the emulator** (~15 files + unit tests). The emulator is the only new engineering;
everything else is "do what BigQuery did, in six places".

## 2. Decisions — each verified, evidence in Appendix A

| Decision | Choice | Why / evidence |
|---|---|---|
| ADO.NET driver | **`ClickHouse.Client` 7.14.0** (HTTP) | Has `ClickHouseConnection(string connectionString, HttpClient httpClient)` (reflected), so the emulator is an `HttpMessageHandler` with no ports or lifecycle. Octonica.ClickHouseClient has no such seam (see old plan §0.1). |
| Kronikol tracking | **`Kronikol.Extensions.ClickHouse` 3.0.72** | On nuget.org since 3.0.43. `DbConnection` decorator: `connection.WithClickHouseTestTracking(options)` → `TrackingClickHouseConnection`. Works for either driver by matching the type name `ClickHouseConnection`. Its `UnifiedSqlClassifier` already knows ClickHouse dialect. We use the manual-wrap API, **not** `AddClickHouseTestTracking` (that decorates `DbConnection` DI registrations; `src` registers a factory instead). |
| In-memory engine | **DuckDB.NET.Data.Full 1.5.5** (net8.0/net10.0; win-x64, linux-x64, osx, arm64 natives) | Appendix A.3: `$name` parameters, `quantile_cont`, `CAST(count(*) AS UBIGINT)`, rows-affected on INSERT/DELETE all work. Behind `IClickHouseQueryEngine` so it stays a one-file swap. |
| Emulator packaging | **Separate in-repo project `tests/InMemoryEmulator.ClickHouse/`**, no BreakfastProvider references | House pattern is a published package (`InMemoryEmulator.BigQuery`, `Spanner.InMemoryEmulator`); a separate `.csproj` from day one makes extraction a directory move. |
| Docker image | **`clickhouse/clickhouse-server:25.8-alpine`** (LTS line; verified tag) | Appendix A.2: entrypoint runs `/docker-entrypoint-initdb.d/*.sql` (and `CREATE DATABASE $CLICKHOUSE_DB`) against a temporary server *before* `exec`ing the real one, so `service_healthy` implies the schema exists. `wget` is present for the healthcheck. Server reports version `25.8.33.6`, timezone `UTC` with `TZ=UTC`. |
| DDL single source of truth | **One `.sql` file** used by the Docker init and by the emulator | Removes the "passes InMemory, fails Docker" schema-drift class. |
| Delete semantics | **Lightweight `DELETE FROM … WHERE …`** | 25.8 defaults: `enable_lightweight_delete=1`, `lightweight_deletes_sync=2` — the row is gone from the next SELECT (verified through the driver). `ALTER TABLE … DELETE` is an async mutation (`mutations_sync=0`) and would make "no longer listed" flaky. DuckDB runs `DELETE FROM` untranslated. |
| Dates | `DateTime` columns (UInt32 unix seconds), container `TZ=UTC`, services use `DateTime.UtcNow` | The driver sends `DateTime` parameters as `yyyy-MM-ddTHH:mm:ss` **with no zone and no conversion**; the server interprets them in its timezone. Reads come back `Kind=Utc`. Keep everything UTC end to end. |
| Numbers | `Float64` only; `count()` cast to `UInt64`; never `sum()` an integer column | DuckDB `sum(BIGINT)` → `HUGEINT` (`System.Numerics.BigInteger`), no cheap RowBinary mapping. |
| Rows affected | Accept that the driver's `ExecuteNonQuery` returns **0** for INSERT and DELETE | True against real ClickHouse too (Appendix A.2), so Kronikol shows `0 rows affected` in both lanes and parity is automatic. Emit `X-ClickHouse-Summary` anyway for `QueryStats` fidelity. |
| Fetcher delegate | Wrap in a lambda | `SqlTrackingOptionsBase.CurrentTestInfoFetcher` is `Func<(string Name, string Id)?>?` (nullable tuple); `CurrentTestInfo.Fetcher` is `Func<(string Name, string Id)>`. No delegate variance for value types, so `CurrentTestInfoFetcher = () => currentTestInfoFetcher()` — a bare assignment will not compile. |
| Octonica front-end (old plan Stage 2) | **Deferred** | Justified only by external teams; belongs in the extracted emulator repo. |
| Java twin (`java-twin` branch) | **Out of scope** | Would be the same feature in Kronikol4J terms; separate work. |

## 3. The feature

Database `kitchen_analytics`, three MergeTree tables. Production/Docker connection string
`Host=localhost;Port=8123;Database=kitchen_analytics`; in Docker-compose networks `Host=clickhouse.local`.

### 3.1 DDL — `docker/clickhouse/init/001-kitchen-analytics.sql`

```sql
CREATE DATABASE IF NOT EXISTS kitchen_analytics;

CREATE TABLE IF NOT EXISTS kitchen_analytics.order_timings
(
    timing_id     String,
    order_id      String,
    station       String,
    item_type     String,
    prep_seconds  Float64,
    recorded_at   DateTime
)
ENGINE = MergeTree()
ORDER BY (station, recorded_at);

CREATE TABLE IF NOT EXISTS kitchen_analytics.equipment_readings
(
    reading_id    String,
    equipment_id  String,
    metric        String,
    value         Float64,
    unit          String,
    recorded_at   DateTime
)
ENGINE = MergeTree()
ORDER BY (equipment_id, recorded_at);

CREATE TABLE IF NOT EXISTS kitchen_analytics.service_times
(
    service_id    String,
    order_id      String,
    item_type     String,
    wait_seconds  Float64,
    served_at     DateTime
)
ENGINE = MergeTree()
ORDER BY (item_type, served_at);
```

This exact file was run through the container in Appendix A.2 (`SHOW TABLES FROM kitchen_analytics` lists
all three). Add `docker/clickhouse/init/*.sql text eol=lf` to `.gitattributes` so a Windows checkout
never feeds CRLF to the init client.

### 3.2 Sub-feature A — Order Timings (`/order-timings`) — mirrors Ingredient Usage

| Endpoint | SQL (exact — this fixes the translator's scope) |
|---|---|
| `POST /order-timings` → 201 | `INSERT INTO order_timings (timing_id, order_id, station, item_type, prep_seconds, recorded_at) VALUES ({timingId:String}, {orderId:String}, {station:String}, {itemType:String}, {prepSeconds:Float64}, {recordedAt:DateTime})` |
| `GET /order-timings/summary` → 200 | `SELECT station, avg(prep_seconds) AS avg_prep_seconds, quantile(0.95)(prep_seconds) AS p95_prep_seconds, count() AS timing_count FROM order_timings GROUP BY station ORDER BY avg_prep_seconds DESC` |
| `GET /order-timings/station/{station}` → 200 | `SELECT timing_id, order_id, station, item_type, prep_seconds, recorded_at FROM order_timings WHERE station = {station:String} ORDER BY recorded_at DESC` |

All three ran against real ClickHouse in Appendix A.2; result types are `String`, `Float64`, `Float64`,
`UInt64` for the summary and `String ×4, Float64, DateTime` for the list.

Request `OrderTimingRequest { string? OrderId; string? Station; string? ItemType; decimal PrepSeconds }`;
validator: strings `NotEmpty().MaximumLength(200)`, `PrepSeconds > 0`. Response
`OrderTimingResponse { TimingId, OrderId, Station, ItemType, PrepSeconds, RecordedAt }`;
`OrderTimingSummaryResponse { Station, AvgPrepSeconds, P95PrepSeconds, TimingCount }`.

### 3.3 Sub-feature B — Equipment Readings (`/equipment-readings`) — mirrors Ingredient Waste

| Endpoint | SQL |
|---|---|
| `POST /equipment-readings` → 201 | `INSERT INTO equipment_readings (reading_id, equipment_id, metric, value, unit, recorded_at) VALUES ({readingId:String}, {equipmentId:String}, {metric:String}, {value:Float64}, {unit:String}, {recordedAt:DateTime})` |
| `GET /equipment-readings/equipment/{equipmentId}` → 200 | `SELECT reading_id, equipment_id, metric, value, unit, recorded_at FROM equipment_readings WHERE equipment_id = {equipmentId:String} ORDER BY recorded_at DESC` |
| `DELETE /equipment-readings/{readingId}` → 204 | `DELETE FROM equipment_readings WHERE reading_id = {readingId:String}` |

Request `EquipmentReadingRequest { string? EquipmentId; string? Metric; decimal Value; string? Unit }`;
validator: strings `NotEmpty().MaximumLength(200)`, `Value > 0`. Response `EquipmentReadingResponse`
with `ReadingId` + `RecordedAt`.

### 3.4 Sub-feature C — Service Times (Kafka-driven) — mirrors Recipe Costs

`OrderServedEvent { Guid ServiceId; Guid OrderId; string ItemType; decimal WaitSeconds; DateTime ServedAt }`
on topic `breakfast_orders_served`, key `OrderServedEvent` in `KafkaConfig.ConsumerConfigurations`
(and `ProducerConfigurations`, for symmetry with `RecipeCostCalculatedEvent`).

`KafkaOrderServedConsumerService : BackgroundService` (copy of `KafkaRecipeCostConsumerService`) →
`IServiceTimeAnalysisService.ProcessOrderServedAsync(...)`:

1. `INSERT INTO service_times (service_id, order_id, item_type, wait_seconds, served_at) VALUES ({serviceId:String}, {orderId:String}, {itemType:String}, {waitSeconds:Float64}, {servedAt:DateTime})` — ClickHouse arrow
2. `INotificationClient.SendOrderConfirmationAsync(orderId.ToString(), itemType, 1, ct)` — gRPC arrow
3. `GET status/{orderId}` on `httpClientFactory.CreateClient(HttpClientNames.KitchenService)` — HTTP arrow. The Kitchen fake maps `GET /status/{orderId:guid}`, and `RequestCapturingHandler` records every outbound request per client name, so the assertion is the same shape as the existing `/prepare` one.

Why this flow is attributed to the right test with no HTTP request in flight: the publish step wraps
`ConsumedKafkaMessageStore.Add` in `TestIdentityScope.Begin(...)`, the in-memory consumer handles the
message synchronously inside that scope, Kronikol's `TestInfoResolver` resolves HTTP context → fetcher →
`TestIdentityScope.Current`, and the fakes' `RequestCapturingHandler` falls back to
`TestIdentityScope.Current?.Id` for the request id. Both were read in source; the recipe-cost flow
relies on exactly the same chain.

Health check: `ClickHouseHealthCheck(IClickHouseConnectionFactory)` opens a connection and
`ExecuteScalarAsync("SELECT 1")` (returns `UInt8` 1) — a straight copy of `SpannerHealthCheck`.

### 3.5 The `src` rule that keeps tracking transparent

Services code against **`DbConnection` / `DbCommand` / `DbDataReader` only**: `cmd.CreateParameter()`
with `ParameterName` + `Value`, `{name:Type}` placeholders in the SQL, `ExecuteReaderAsync`,
`ExecuteNonQueryAsync`, `ExecuteScalarAsync`. No `ClickHouse.Client`-specific API in services. This
is what lets the factory return a `TrackingClickHouseConnection` (a plain `DbConnection` subclass) in
test mode with zero changes to `src`.

Read `timing_count` with `Convert.ToInt32(reader["timing_count"])` — it arrives as `UInt64` from both
the emulator and the server, but `Convert` is one less thing that has to be byte-identical. Read
`recorded_at` with `reader.GetDateTime(i)`; it is `Kind=Utc` from both.

**Pre-existing quirk, decide deliberately.** `AddInfrastructureChecks` resolves each backend's check with
`sp.GetService<XxxHealthCheck>()` and falls back to `NoOpHealthCheck("… not configured.")` — but nothing
in `src` ever registers `BigQueryHealthCheck`, `SpannerHealthCheck`, `MongoDbHealthCheck`, `KafkaHealthCheck`
or `PubSubHealthCheck` in DI, so every one of those checks is the no-op in every lane, including
External SUT. This plan registers `ClickHouseHealthCheck` so that the Docker and External SUT lanes
really probe ClickHouse (`/health` in the SUT container then depends on the `clickhouse` service, which
`depends_on: service_healthy` already guarantees). The InMemory lane still swaps in the no-op via
`ReplaceClickHouseHealthCheckWithNoOp`. Consequence to accept: in the Docker lane every health-check
scenario's diagram gains a `SELECT 1` ClickHouse arrow, which is correct. Registering the other five
checks is a separate follow-up, not part of this feature.

**Exit criteria:** `dotnet build BreakfastProvider.sln` green; the API starts with an empty
`ClickHouseConfig` (NoOp factory, health check "not configured"); the services reference nothing from
the `ClickHouse.Client` namespace.

## 5. Phase 1 — The emulator: `tests/InMemoryEmulator.ClickHouse/`

New class library, `net10.0`, `<Nullable>enable</Nullable>`, namespace `InMemoryEmulator.ClickHouse`.
References `DuckDB.NET.Data.Full` 1.5.5 and `ClickHouse.Client` 7.14.0 (the latter only for

Unit tests go in `tests/BreakfastProvider.Tests.Unit` (currently empty; xUnit v3, AwesomeAssertions):

without a rewrite: `Core/` never references `System.Net.Http`; results cross the boundary as

franca. One unit test asserts the first rule by reflection over the assembly.

### 5.2 `DuckDbClickHouseQueryEngine`

- Single in-memory `DuckDBConnection`, every call under a `SemaphoreSlim(1,1)`. Tests run in parallel;
  serialising sub-millisecond queries is the simplest correct answer.
- `ExecuteDdl` runs translated DDL. `Execute` maps result columns by **CLR type from
  `reader.GetFieldType(i)`** (DuckDB.NET's `GetDataTypeName` returns names like `Varchar`, `Double`,
  `Timestamp`, `UnsignedBigInt`, `BigInt`, `HugeInt`, `Integer`, `Boolean`, `TimestampTz`; keying on
  CLR types is shorter and more stable). If any value in a column is `DBNull`, the type string is
  wrapped as `Nullable(T)` — ClickHouse.Client cannot read a null in a non-Nullable column (Appendix A
  shows `Nullable(String)` round-tripping to `DBNull`).
- DuckDB returns `TIMESTAMP` values as `DateTime` with `Kind=Unspecified` (Appendix A.3); the engine
  re-stamps them `Kind=Utc` before they cross the boundary.
- `ExecuteNonQuery` returns DuckDB's rows affected (1 for the single-row INSERT and DELETE in Appendix A.3)
  — used only for the `X-ClickHouse-Summary` header.
- Error mapping from `DuckDBException.Message` prefixes: `Parser Error` → 62, `Catalog Error` → 60,
  `Binder Error` → 47, anything else → 1000.

### 5.3 `ClickHouseSqlTranslator` — the whole rule list

Every rule gets a unit test. Anything unrecognised throws `NotSupportedException` naming the fragment;
a loud failure in a component test beats a silently wrong aggregate.

| # | ClickHouse | DuckDB |
|---|---|---|
| 1 | `CREATE DATABASE …` | no-op |
| 2 | `ENGINE = MergeTree() ORDER BY (…)` (also `PARTITION BY`, `TTL`, `SETTINGS`) | strip from DDL |
| 3 | `<Database>.` table qualifier (`kitchen_analytics.`) | strip |
| 4 | DDL types `String` / `Float64` / `DateTime` / `UInt32` / `UInt64` / `Int32` / `Int64` / `Nullable(T)` | `VARCHAR` / `DOUBLE` / `TIMESTAMP` / `UINTEGER` / `UBIGINT` / `INTEGER` / `BIGINT` / `T` |
| 5 | `{name:Type}` | `$name` + a `DuckDBParameter` coerced per `Type` (§5.4) |
| 6 | `quantile(p)(x)` | `quantile_cont(x, p)` |
| 7 | `count()` | `CAST(count(*) AS UBIGINT)` |
| 8 | `SELECT 1` | pass through |
| 9 | `DELETE FROM … WHERE …`, `INSERT … VALUES`, `SELECT … GROUP BY … ORDER BY`, `avg()` | pass through |
| 10 | trailing `FORMAT <x>` | stripped by the handler before translation |

Result type map (CLR → ClickHouse type string): `string→String`, `double→Float64`,
`DateTime→DateTime`, `ulong→UInt64`, `long→Int64`, `int→Int32`, `uint→UInt32`, `byte→UInt8`,
`bool→UInt8`, `System.Numerics.BigInteger→throw` (with a message pointing at the "don't sum integers"
rule), `DateTimeOffset→throw` (DuckDB `now()` is `TimestampTz`; don't use it).

### 5.4 Parameters — exactly what the driver sends

Captured in Appendix A. Placeholders stay in the SQL text verbatim; values travel as query-string
entries `param_<name>=<text>`:

| CLR value | On the wire | Binder conversion (by declared `{name:Type}`) |
|---|---|---|
| `"Griddle-abc"` | `param_station=Griddle-abc` | `String` → as-is |
| `1.5d` | `param_min=1.5` | `Float64` → `double.Parse(InvariantCulture)` |
| `new DateTime(2026,9,2,10,11,12, Utc)` | `param_since=2026-09-02T10%3a11%3a12` | `DateTime` → `DateTime.ParseExact("yyyy-MM-ddTHH:mm:ss", Invariant)` then `SpecifyKind(Utc)` |
| `Guid` | `param_oid=0f8fad5b-…` | `String` → as-is |

The driver applies **no timezone conversion** when formatting `DateTime` values, so services must
supply UTC values (`DateTime.UtcNow`); the server (TZ=UTC) and the emulator then agree.

### 5.5 HTTP front-end — the contract (all from Appendix A)

What arrives: `POST http://<host>:<port>/?enable_http_compression=<bool>&default_format=RowBinaryWithNamesAndTypes&database=<db>[&param_x=…]`,
header `Authorization: Basic <user:password>` (ignore), body = the SQL text (`Content-Type: text/sql`;
`text/plain` for the handshake). With the driver's default `Compression=true` the body is
`Content-Encoding: gzip` and `Accept-Encoding: gzip,deflate` is sent; with `Compression=false` neither.

`InMemoryClickHouseHandler.SendAsync`:

1. If `Content-Encoding: gzip`, decompress with `GZipStream` (a few lines; do it rather than refuse).
   Never compress responses — the driver accepts identity encoding regardless of `Accept-Encoding`.
2. SQL from the body, else `query=`. Strip a trailing `FORMAT <name>`; otherwise use `default_format`;
   otherwise `RowBinaryWithNamesAndTypes`. Read `param_*`. Ignore `database`, `query_id`, `session_id`,
   `enable_http_compression`, `compress`.
3. Handshake: body `SELECT version(), timezone() FORMAT TSV` → `200`, body `25.8.33.6\tUTC\n`
   (match the Docker image so `ServerVersion` reads the same in both lanes). Get this wrong and every
   test fails inside `OpenAsync`.
4. Otherwise translate → engine → encode. Any statement that returns a result set → `200` with
   `RowBinaryWithNamesAndTypes` (the driver never appends a `FORMAT` clause itself). INSERT/DELETE → `200`,
   empty body, plus `X-ClickHouse-Summary: {"read_rows":"0","read_bytes":"0","written_rows":"<n>","written_bytes":"0","total_rows_to_read":"0","result_rows":"0","result_bytes":"0","elapsed_ns":"0"}`
   (string-valued numbers, exactly as the server emits).
5. Always add `X-ClickHouse-Query-Id`, `X-ClickHouse-Timezone: UTC`, `X-ClickHouse-Server-Display-Name: inmemory`.
6. Errors: status **400 for code 62**, **404 for codes 60 and 47**, 500 otherwise — this is the server's
   own mapping — with header `X-ClickHouse-Exception-Code: <code>` and body
   `Code: <code>. DB::Exception: <message>. (<NAME>) (version 25.8.33.6 (official build))`. The driver
   raises `ClickHouse.Client.ClickHouseServerException` whose `Message` is the body.

`RowBinaryWriter` encodings: column count varint; names and type strings as varint-length + UTF-8
(`BinaryWriter.Write(string)` produces exactly this; `ClickHouse.Client.Formats.ExtendedBinaryWriter`
is public if you prefer its `Write7BitEncodedInt`); then per row, per column: `String` varint+UTF-8;
`UInt8` 1 byte; `Int32`/`UInt32` 4 bytes LE; `Int64`/`UInt64` 8 bytes LE; `Float64` IEEE-754 LE;
`DateTime` `UInt32` unix seconds; `Nullable(T)` one flag byte (`0` = value follows, `1` = null, nothing
follows). Appendix A shows this exact layout being read back by the driver with the right CLR types.

**Test oracle:** the driver itself. Encode → hand the bytes to a real `ClickHouseConnection` over a
stub handler → assert the materialised CLR values. Hand-written expected bytes only for the varint
127/128 boundary and the `Nullable` flag.

**TDD order:** `TsvWriter` → `RowBinaryWriter` (`String` → `UInt64` → `Float64` → `DateTime` → `UInt8`
→ `Nullable`) → translator rules 1–9, one test each → `ClickHouseParameterBinder` (the four rows of
§5.4) → engine round-trip (DDL, insert, select, delete, error prefixes) → handler handshake → handler
SELECT → handler INSERT with the summary header → handler gzip body → handler error statuses →
**first end-to-end**: `new ClickHouseConnection(server.ConnectionString, server.CreateHttpClient())`
opens, inserts, reads back, deletes, and surfaces a `ClickHouseServerException` for `SELECT * FROM nope`
— in-process, on Windows, Docker stopped.

## 12. Risks and traps

| Risk | Likelihood | Mitigation |
|---|---|---|
| Fetcher delegate type mismatch (`Func<(string,string)>` vs `Func<(string,string)?>`) | Certain if assigned directly | Lambda wrapper (§6.1) |
| `DateTime` parameter parsed with the wrong format or zone | Medium | Pinned format `yyyy-MM-ddTHH:mm:ss`, no zone (§5.4); services use `DateTime.UtcNow`; unit test with the captured string |
| DuckDB integer widths (`HUGEINT`, `BIGINT` vs `UInt64`) | Medium | Only `avg`/`quantile` over `Float64`; `count()` cast rule; `BigInteger` throws |
| `ALTER TABLE … DELETE` async → flaky "no longer listed" | High if chosen | Lightweight `DELETE FROM` (verified immediate) |
| Timezone skew shifts `recorded_at` between lanes | Medium | `TZ=UTC` in the container, handshake reports `UTC`, DuckDB timestamps re-stamped `Utc`, services use `UtcNow` |
| Translator gap discovered mid-feature | Medium | Seven statements fixed up front (§3); anything else throws naming the fragment |
| Compressed request body | Low | Handler decompresses gzip; emulator connection string sets `Compression=false` anyway |
| Stale Docker container set reused without ClickHouse | Low | `IsClickHouseReady` in `AreExistingContainersUsable` |
| CRLF in the init SQL on Windows checkouts | Low | `.gitattributes` `eol=lf` |
| Six duplicated fixture blocks drift | Low | Same block, one commit; grep `RunWithAnInMemoryBigQuery` to find all six |
| Init script semantics change in a future image | Low | Pin `25.8-alpine`; the `SHOW TABLES` exit check catches it |
| `X-ClickHouse-Summary` omitted | Cosmetic | Driver's `ExecuteNonQuery` returns 0 regardless; header only feeds `QueryStats` |
| `ClickHouseHealthCheck` never registered, so `/health` silently no-ops (as the other five backends do today) | High if copied blindly | Register it when configured (§4 note); the Docker-lane health scenario diagram shows the `SELECT 1` arrow as proof |
| `OrderServedEvent` missing from `docs/asyncapi.json` | Low | Implement `IKafkaEvent` with `[Description]` attributes (§4); the doc is reflection-driven |

### A.4 Package and API facts

- `ClickHouse.Client` 7.14.0 constructors: `()`, `(string)`, `(string, HttpClient)`, `(string, IHttpClientFactory)`. Public: `ClickHouse.Client.Formats.ExtendedBinaryWriter`, `ClickHouse.Client.Copy.ClickHouseBulkCopy`, `ClickHouse.Client.ADO.ClickHouseConnectionStringBuilder` (properties include `Compression`, `Database`, `Host`, `Port`, `Username`, `Password`, `UseSession`, `SessionId`, `Timeout`, `UseServerTimezone`, `UseCustomDecimals`). `ClickHouseCommand` exposes `QueryId`, `QueryStats`, `CustomSettings`, `ExecuteRawResultAsync`.
- `Kronikol.Extensions.ClickHouse` 3.0.72 on nuget.org (first release 3.0.43, 2026-06-20). `ClickHouseTrackingOptions : SqlTrackingOptionsBase` (`Kronikol.Sql`): `ServiceName="ClickHouse"`, `Verbosity` (`SqlTrackingVerbosityLevel`), `CurrentTestInfoFetcher: Func<(string Name, string Id)?>?`, `HttpContextAccessor`, `LogParameters=false`, `LogSqlText=true`, `LogResponseContent=true`, `MaxResponseRows=10`, `MaxValueDisplayLength=500`, `ResponseDetail=RowCountAndColumns`, `ExcludedOperations`. `TrackingClickHouseConnection` forwards `Open/Close/CreateCommand/BeginTransaction/Dispose(Async)` to the inner connection; `TrackingClickHouseCommand` logs the request before execution (SQL text, `FormattedDataSource` = `DataSource` or `"localhost"`, database, `name=value` parameter list when `LogParameters`) and the response after (`N rows affected` for non-query; a `TrackingDbDataReader` that counts rows/columns for readers; the scalar's string for scalars).
- `DuckDB.NET.Data.Full` 1.5.5: `lib/net8.0` and `lib/net10.0`; natives for `win-x64`, `win-arm64`, `linux-x64`, `linux-arm64`, `osx`.
- Docker Hub tags present: `25.8-alpine`, `25.8.33.6-alpine` (and `26.3.x`); image contains `/usr/bin/wget`.
- Kronikol `TestInfoResolver.Resolve(httpContextAccessor, fetcher)` order: HTTP request headers → `CurrentTestInfoFetcher` → `TestIdentityScope.Current` → `TestIdentityScope.GlobalFallback`. `TrackingDbDataReader` emits its response content once, on end-of-rows or on Close/Dispose.
- BreakfastProvider `RequestCapturingHandler` (the fakes' request store) takes the request id from the `ComponentTestRequestId` header, else `TestIdentityScope.Current?.Id`, and records every method including GET.
- BreakfastProvider `AsyncApiDynamicConfigurationProviderFilter` builds the AsyncAPI document by reflecting over all `IKafkaEvent` / `IPubSubEvent` / `IEventGridEvent` / `IEventHubEvent` implementations; `IKafkaEvent.GetAsyncApiMetadata` uses the type name as channel name and `[Description]` attributes for text.
- BreakfastProvider registers no `*HealthCheck` class in DI; `AddInfrastructureChecks` falls back to `NoOpHealthCheck` for Kafka, Pub/Sub, Spanner, MongoDB and BigQuery in every lane.
- The SUT under test reads `appsettings.componenttests.json` (via `ConfigurationBuilderExtensions` and each fixture's `ConfigureAppConfiguration`), so `ClickHouseConfig` in the test settings is what `AddClickHouse` binds.

The recording handler that produced A.1 (the rest of the program is ordinary ADO.NET calls):

```csharp
sealed class RecordingHandler : HttpMessageHandler
{
    public bool SendSummary = true;
    protected override async Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken ct)
    {
        byte[] bytes = request.Content is null ? [] : await request.Content.ReadAsByteArrayAsync(ct);
        if (request.Content?.Headers.ContentEncoding.Contains("gzip") == true)
        {
            using var gz = new System.IO.Compression.GZipStream(new MemoryStream(bytes), System.IO.Compression.CompressionMode.Decompress);
            using var ms = new MemoryStream(); gz.CopyTo(ms); bytes = ms.ToArray();
        }
        var sql = System.Text.Encoding.UTF8.GetString(bytes);
        Console.WriteLine($">> {request.Method} {request.RequestUri}\n   {string.Join("\n   ", request.Headers.Concat(request.Content?.Headers ?? Enumerable.Empty<KeyValuePair<string, IEnumerable<string>>>()).Select(h => $"{h.Key}: {string.Join(",", h.Value)}"))}\n   BODY: {sql}");

        HttpResponseMessage resp;
        if (sql.Contains("version()"))
            resp = new(System.Net.HttpStatusCode.OK) { Content = new StringContent("25.8.33.6\tUTC\n") };
        else if (sql.Contains("BAD"))
        {
            resp = new(System.Net.HttpStatusCode.BadRequest) { Content = new StringContent("Code: 62. DB::Exception: Syntax error: failed at position 8: BAD SYNTAX. (SYNTAX_ERROR) (version 25.8.33.6 (official build))") };
            resp.Headers.TryAddWithoutValidation("X-ClickHouse-Exception-Code", "62");
        }
        else if (sql.TrimStart().StartsWith("INSERT", StringComparison.OrdinalIgnoreCase))
        {
            resp = new(System.Net.HttpStatusCode.OK) { Content = new ByteArrayContent([]) };
            if (SendSummary) resp.Headers.TryAddWithoutValidation("X-ClickHouse-Summary", "{\"read_rows\":\"0\",\"read_bytes\":\"0\",\"written_rows\":\"1\",\"written_bytes\":\"0\",\"total_rows_to_read\":\"0\",\"result_rows\":\"0\",\"result_bytes\":\"0\",\"elapsed_ns\":\"0\"}");
        }
        else
        {
            // RowBinaryWithNamesAndTypes: String, Float64, DateTime, UInt64, Nullable(String); two rows
            var ms = new MemoryStream(); var w = new BinaryWriter(ms, System.Text.Encoding.UTF8);
            w.Write7BitEncodedInt(5);
            foreach (var n in new[] { "timing_id", "prep_seconds", "recorded_at", "cnt", "note" }) w.Write(n);
            foreach (var t in new[] { "String", "Float64", "DateTime", "UInt64", "Nullable(String)" }) w.Write(t);
            var epoch = (uint)new DateTimeOffset(2026, 9, 2, 10, 11, 12, TimeSpan.Zero).ToUnixTimeSeconds();
            w.Write("id-1"); w.Write(2.5d); w.Write(epoch);      w.Write(3UL);            w.Write((byte)0); w.Write("hello");
            w.Write("id-2"); w.Write(0.25d); w.Write(epoch + 60); w.Write(ulong.MaxValue); w.Write((byte)1);
            resp = new(System.Net.HttpStatusCode.OK) { Content = new ByteArrayContent(ms.ToArray()) };
        }
        resp.Headers.TryAddWithoutValidation("X-ClickHouse-Timezone", "UTC");
        return resp;
    }
}
```
